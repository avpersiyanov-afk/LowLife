# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A pyRevit extension (IronPython/CPython 2 scripts run inside Revit). There is no build step, package manager, or linter. `tests/` holds pytest unit tests for the Revit-free logic in `lib/lowlife/` (see `tests/README.md`). "Running" the code means loading it into Revit through pyRevit.

## Extension layout requirement (important, non-obvious)

pyRevit installs extensions added by a GitHub URL by cloning the repo directly into `%APPDATA%\pyRevit\Extensions\<name>.extension\` — pyRevit itself supplies the `.extension` wrapper folder. Because of this, **`LowLife.tab` must stay at the repo root**, not nested inside a `LowLife.extension/` folder in the repo. Wrapping it again produces a double-nested `.extension\.extension\` path and the tab won't load. Do not "fix" this by re-adding an extension wrapper folder.

## Deploying/testing a change

The user updates their Revit installation by re-pulling this repo via pyRevit's extension manager (GitHub URL), then reloading pyRevit / restarting Revit. There is no local Revit instance to run scripts against in this environment — changes can only be verified by reading the code, not by executing it. Say so explicitly rather than claiming a script "works."

One exception: `LowLife.tab/SCS.panel/SeedMySettings.pushbutton/` is local-only (excluded via `.gitignore`, along with `*.local.md`) — it hardcodes one project's real parameter/family names so the user doesn't have to fill the settings form by hand. Never commit real parameter names from that file or from `docs/scs-parameters.local.md`; the tracked docs (`docs/scs-panel.md`) intentionally describe *what* parameters are needed without naming them.

## Shared library (`lib/`)

`lib/` sits next to `LowLife.tab` at the extension root, so pyRevit adds it to `sys.path` automatically — any `script.py` can `from lowlife.xxx import yyy` with no path setup. See `lib/README.md` for the full function-by-function reference; the important structural point is the split between:
- **Discipline-agnostic helpers** (`geometry.py`, `params.py`, `selection.py`, `electrical_circuits.py`, `manual_circuits.py`) — pure Revit-API utilities usable by any future panel. `electrical_circuits.py` is Revit's `ElectricalSystem.Create`/`SelectPanel` wrapper; `manual_circuits.py` is the full "pick panel, pick devices, build one circuit per device" button flow used by the per-discipline CircuitsSCS/CircuitsSKUD panels' buttons. CircuitsSPA.panel used to be one of them but now builds loop circuits by device address instead (same `fire_alarm_settings`/`fire_alarm_buttons.build_loop_circuits` logic as SPS/SOUE, third system `"SPA"`, workset filter keyword defaults to «СПА»).
- **Settings plumbing** (`settings_core.py`) — every button's JSON settings file goes through `settings_core.JsonStore` (modules keep `_settings_file_path`/`_read_all`/`_write_all` only as aliases onto it; don't re-add hand-written copies). A new button whose settings are just text/number fields should declare a `settings_core.TextSettings` with `TextField`/`NumberField`s (see `room_lots_settings.py`) instead of hand-building a WPF window.
- **SCS-specific logic** (`scs.py`, `scs_addressing.py`, `scs_circuits.py`, `scs_settings.py`) — everything for the `SCS.panel` toolset (structured cabling). New disciplines (fire alarm, security) should get their own `scs_*`-style module rather than being folded into these.

Button scripts (`script.py`) are meant to stay thin orchestration — collect elements, call library functions, write results in a transaction. Don't grow business logic back into a button script; extract it into `lib/lowlife/` instead, matching the existing pattern.

## SCS.panel pipeline

Three buttons operate on the same marker-element ecosystem and must be run in order, each consuming the previous one's output:
1. **PlaceRouteNodes** ("Узлы трассы") — classifies points along route lines into 4 categories (`riser > panel > device > route` priority) and inserts/updates the matching Generic Model family instance at each point.
2. **RenumberAddresses** ("Адреса узлов") — builds a geometric graph from route/riser markers only and BFS-assigns address strings (`F1.3`) from panel/riser roots.
3. **SyncCircuitsAndLengths** ("Синхронизация цепей") — builds a graph from the *address* parameter chain (not geometry) and A*-routes each electrical circuit from its panel to its device, writing lengths/labels/numbers.

Key architectural points that aren't obvious from any single file:
- All buttons share one settings file (`%APPDATA%\pyRevit\LowLifeSCS_settings.json`, plain JSON — deliberately *not* `pyrevit.script.get_config()`, which didn't reliably share a config section across different `script.py` files in testing; don't reintroduce that approach without re-verifying). Each button edits it through its own Shift+click, not a shared window: `scs_settings.get_settings_interactive(doc, keys=[...])` takes an explicit `keys` list and renders only those fields (SCS/SKUD/fire-alarm SetupParameters-style dialogs used to be one shared form for the whole panel — that pattern is gone; every consuming button now owns its own scoped popup). A button's `keys` list should match what it passes to `scs_settings.require(settings, [keys...])` right after loading settings, plus any extra keys it reads but doesn't strictly require.
- SCS.panel/SetupParameters no longer edits settings at all — it only checks/adds shared-parameter bindings to categories from the connected ФОП file (reads settings silently via `get_settings_silent()`). SKUD.panel/SetupParameters is the same pattern. SOUE/SPS/CircuitsSPA had no such binding step, so their SetupParameters buttons were deleted outright.
- `scs.py`'s default parameter/family-name constants are intentionally blank strings/lists — these are per-project conventions (e.g. a project's own prefixed shared parameters) and must never be hardcoded into tracked files. Classification *keywords* (коннектор, розетка, панель, стояк, ...) are treated as generic vocabulary and do get sensible defaults.
- `PlaceRouteNodes` and `RenumberAddresses`/`SyncCircuitsAndLengths` guard against stale data: `clear_stray_address_params` wipes address parameters left on elements that are no longer route/riser-typed (e.g. after a device's family got split out of a shared marker family in an earlier project iteration), and `SyncCircuitsAndLengths` reports (rather than silently overwrites) duplicate addresses.

## IronPython/Revit-API gotchas already worked around here

- `el.Name` throws an ambiguous-binding error on some element types (notably `Family`/`FamilySymbol`) under IronPython; use `Element.Name.GetValue(el)` instead (see `_safe_element_name` in `scs_settings.py`).
- Listing all loaded family types of a category (including unplaced ones) must go through `FilteredElementCollector(doc).OfClass(Family)` → `family.GetFamilySymbolIds()`, not `FilteredElementCollector(doc).OfCategory(...).OfClass(FamilySymbol)`, which can miss unplaced types.
- WPF settings windows: never set `Topmost` on a window that will itself open another WPF window (e.g. `forms.SelectFromList`) — the child window gets stuck behind it with no way to bring it forward.
- This is Python 2 (IronPython): `unicode(...)` and `u"..."` literals are used deliberately throughout; don't "modernize" to Python 3 string handling.
- IronPython's `str.format` rejects a precision spec on an `int` (`u"{:.0f}".format(1920)` raises "Precision not allowed in integer format specifier", while CPython accepts it). Convert to `float(...)` before formatting with `{:.Nf}` — e.g. values from `_as_int` or `Parameter.AsInteger()`.

## Notes.panel («Заметки по проекту»)

Library is a separate package `lib/pnotes/` (not `lib/lowlife/`); notes live in a shared Google Sheet via an Apps Script web app (`docs/notes/Code.gs`, setup in `docs/notes-panel.md`). The connection URL/token is per-user (`%APPDATA%\pyRevit\ProjectNotes\config.json`, entered in the «Настройка» window) — never commit a root `config.json` (gitignored; `config.example.json` is the empty template). Open-model reminders are appended to `hooks/doc-opened.py` in their own `try/except` so they can never break the existing hook logic or model opening.

Windows never wait on the network before opening: «Сводка»/«Новая заметка»/«Настройка» start from the cached settings (`core.get_settings_fast()`) and cached notes (`core.cached_notes()`), and every sheet request made while a window is open goes through `ui.in_background(window, work, done)` — `work` runs on a background thread (network and files only, never the Revit API), `done` runs on the window's thread via `Dispatcher`; closing the window aborts the requests (`core.abort_requests()`) and joins the threads. Don't put synchronous `core.call(...)` back in front of `ShowDialog()`. Saving a new note doesn't wait at all: the window queues it (`core.queue_note`) and closes, then `core.send_queue_detached()` sends the queue on a thread that outlives the button script — that's why NewNote runs on a persistent pyRevit engine (`engine: persistent` in its `bundle.yaml` plus `__persistentengine__` in `script.py`); detached requests use `track=False` so a window closing doesn't abort them. Every write to `queue.json` goes through `core._QueueLock` (an AppDomain-wide lock, since each button's engine has its own copy of the module), and `flush_queue` removes only the notes it actually sent. Summary actions (status, edit, answer) are optimistic: `SummaryWindow._apply` updates the list at once, sends in the background, rolls back on error, keeps the window from closing until sends finish, and re-applies its changes over a sheet load that started before they were saved. `core.call` retries once on transient failures (connection drops, 5xx/429, an HTML error page) — every Code.gs action is safe to repeat (`add` dedupes by id); keep it that way when adding actions.

Possible future step (not done — the user decided against it for now): modeless «Сводка»/«Новая заметка» so the user can keep working in Revit with the window open. What it needs: `Show()` instead of `ShowDialog()` plus a persistent pyRevit engine for those buttons (`persistent` in `bundle.yaml`), otherwise the script's handlers die when the button script ends; every Revit API call from the window (summary «Показать» — select/show elements, «Перейти на вид»; reading the active view and selection for a new note — better taken at «Сохранить» than at window open) must go through `ExternalEvent`; one window instance per button (a second click brings the open one forward); the summary must cope with its model being closed or another document becoming active (the actions report that the model is gone instead of failing). «Настройка» reads «Сведения о проекте» directly and should stay modal.

The «Обратная связь» button (`_Themes.panel/Feedback`, `lib/pnotes/feedback.py`) reuses the same HTTP plumbing but posts to a *separate*, author-owned sheet (`docs/feedback/Code.gs`, append-only — nothing can be read back through it; setup in `docs/feedback-panel.md`). Its web-app URL is the one deliberately tracked value (`FEEDBACK_URL`), since every user must reach it without configuring anything; there is no token. Panel/button choices come from the extension folders via `lowlife.ribbon_catalog`, so new buttons appear automatically.

## Icons

Pushbutton icons are 96×96 PNGs generated programmatically with Pillow rather than hand-drawn or fetched, in the brand palette of the logo, in two versions per button: `icon.png` for Revit's light theme (light grey rounded square, near-black line-art glyph) and `icon.dark.png` for the dark theme (black rounded square, white glyph) — pyRevit picks `icon.dark.png` by itself when Revit is in dark theme. Both use the logo's orange accent (`#F08C28`; red only for delete buttons). The set is produced by `docs/brand/restyle_icons.py` from icons drawn in the earlier light-background/blue-glyph style (palette-only recolour, glyphs untouched; it skips buttons that already have `icon.dark.png`, so it is safe to re-run). For a new button (or to replace an icon whose picture doesn't match what the button does): add a drawing function to `docs/brand/draw_icons.py` (draws in the old light/blue palette) and register it in `ICONS` — running that script writes `icon.png`, drops the stale `icon.dark.png` and calls `restyle_icons.py`, which writes both versions. Keep the picture about what the button actually does (e.g. loop circuits = panel + closed loop with devices, not the address «F1.2» glyph; diagnostics = the subject under a magnifier, not a bare checkmark).

Branding lives in `docs/brand/`: the logo is the «⅃Γ» monogram (white mirrored L + orange upside-down L on a black rounded square), generated by `docs/brand/make_brand.py` along with the About button's `icon.png`/`logo.png`. The wordmark (`lowlife-wordmark-source.png`) is the user's own artwork — keep its letters exactly as drawn (the flipped/rotated letters are intentional); the script only crops and cleans it for the README. In the About window the wordmark is set in a font, not shown as an image: `about.WORDMARK_LETTERS` lists the letters, their transforms and accent flag (mirrored L, o, w, the same mirrored L rotated 180° = «Γ» in orange like the monogram, i, capital F rotated 135° clockwise, e) and `wordmark_wpf.build_image()` builds a WPF `DrawingImage` from the font's glyph outlines (Century Gothic Bold, falling back to Segoe UI). `make_brand.py` likewise tints the «Γ» of the README artwork orange (colour only, shapes untouched). The first ribbon panel (`_Themes.panel`, titled «LowLife») starts with the About button; `_Themes.panel` is not in `panel_themes.THEMES`, so it stays visible under every theme.

# Русская версия

Этот файл — ориентир для Claude Code (и для людей) при работе с кодом в этом репозитории.

## Что это

pyRevit-расширение (скрипты IronPython/CPython 2, выполняются внутри Revit). Нет ни шага сборки, ни менеджера пакетов, ни линтера. В `tests/` — pytest-тесты для логики `lib/lowlife/` без Revit API (см. `tests/README.md`). «Запуск» кода означает его загрузку в Revit через pyRevit.

## Требование к структуре расширения (важно, неочевидно)

pyRevit устанавливает расширения, добавленные по ссылке GitHub, клонируя репозиторий прямо в `%APPDATA%\pyRevit\Extensions\<name>.extension\` — обёртку `.extension` создаёт сам pyRevit. Поэтому **`LowLife.tab` должен оставаться в корне репозитория**, а не быть вложенным в папку `LowLife.extension/` внутри репозитория. Повторное оборачивание даёт двойную вложенность `.extension\.extension\`, и вкладка не загружается. Не «исправляйте» это повторным добавлением папки-обёртки расширения.

## Развёртывание/проверка изменений

Пользователь обновляет расширение в Revit, повторно подтягивая этот репозиторий через менеджер расширений pyRevit (по ссылке GitHub), затем перезагружает pyRevit / перезапускает Revit. В этом окружении нет локального экземпляра Revit, на котором можно было бы запускать скрипты — изменения можно проверить только чтением кода, не выполнением. Явно так и говорите, а не утверждайте, что скрипт «работает».

Исключение: `LowLife.tab/SCS.panel/SeedMySettings.pushbutton/` — локальный файл (исключён через `.gitignore`, вместе с `*.local.md`) — в нём зашиты реальные имена параметров/семейств конкретного проекта, чтобы не заполнять форму настроек вручную. Никогда не коммитьте реальные имена параметров из этого файла или из `docs/scs-parameters.local.md`; отслеживаемая документация (`docs/scs-panel.md`) намеренно описывает, *какие* параметры нужны, без указания конкретных имён.

## Общая библиотека (`lib/`)

`lib/` лежит рядом с `LowLife.tab` на уровне расширения, поэтому pyRevit сам добавляет её в `sys.path` — любой `script.py` может писать `from lowlife.xxx import yyy` без настройки путей. Полный список функций по модулям — в `lib/README.md`; важный структурный момент — разделение на:
- **Хелперы, не привязанные к дисциплине** (`geometry.py`, `params.py`, `selection.py`, `electrical_circuits.py`, `manual_circuits.py`) — чистые утилиты Revit API, пригодные для любой будущей панели. `electrical_circuits.py` — обёртка над `ElectricalSystem.Create`/`SelectPanel`; `manual_circuits.py` — весь сценарий кнопки «выбрать панель, выбрать устройства, построить по цепи на каждое» для кнопок панелей CircuitsSCS/CircuitsSKUD. CircuitsSPA.panel раньше тоже была такой, но теперь строит цепи по адресу устройства — та же логика `fire_alarm_settings`/`fire_alarm_buttons.build_loop_circuits`, что у СПС/СОУЭ, третья система `"SPA"`, ключевое слово рабочего набора по умолчанию «СПА».
- **Обвязка настроек** (`settings_core.py`) — JSON-файл настроек любой кнопки читается/пишется через `settings_core.JsonStore` (в модулях `_settings_file_path`/`_read_all`/`_write_all` остались только алиасами на него; не возвращайте рукописные копии). Новой кнопке, у которой настройки — только текстовые/числовые поля, объявляйте `settings_core.TextSettings` с `TextField`/`NumberField` (см. `room_lots_settings.py`), а не собирайте WPF-окно вручную.
- **Логика, специфичная для СКС** (`scs.py`, `scs_addressing.py`, `scs_circuits.py`, `scs_settings.py`) — всё для набора инструментов `SCS.panel` (структурированная кабельная система). Новые дисциплины (ОПС, СБ) должны получать свой модуль в стиле `scs_*`, а не подмешиваться в существующие.

Скрипты кнопок (`script.py`) должны оставаться тонкой оркестрацией — собрать элементы, вызвать функции библиотеки, записать результат в транзакции. Не давайте бизнес-логике снова разрастаться внутри скрипта кнопки — выносите её в `lib/lowlife/`, по уже устоявшемуся образцу.

## Конвейер SCS.panel

Три кнопки работают с одной и той же экосистемой элементов-маркеров и должны запускаться по порядку, каждая следующая использует результат предыдущей:
1. **PlaceRouteNodes** («Узлы трассы») — классифицирует точки вдоль линий трассы на 4 категории (приоритет `стояк > панель > устройство > маршрут`) и вставляет/обновляет в каждой точке соответствующий экземпляр семейства «Обобщённая модель».
2. **RenumberAddresses** («Адреса узлов») — строит геометрический граф только по маркерам маршрута/стояков и присваивает адреса (`F1.3`) обходом в ширину от корней (панелей/стояков).
3. **SyncCircuitsAndLengths** («Синхронизация цепей») — строит граф по цепочке параметра *адреса* (не по геометрии) и прокладывает каждую электрическую цепь алгоритмом A* от панели до устройства, записывая длины/подписи/номера.

Ключевые архитектурные моменты, не очевидные из одного файла:
- Все кнопки делят один файл настроек (`%APPDATA%\pyRevit\LowLifeSCS_settings.json`, обычный JSON — намеренно **не** через `pyrevit.script.get_config()`, который на практике не гарантированно расшаривал секцию конфига между разными `script.py`; не возвращайтесь к этому подходу, не перепроверив заново). Каждая кнопка редактирует его через свой Shift+клик, а не через общее окно: `scs_settings.get_settings_interactive(doc, keys=[...])` принимает список ключей `keys` и показывает только эти поля (раньше SetupParameters-кнопки СКС/СКУД/пожарных систем были одним общим окном на всю панель — этого больше нет, у каждой рабочей кнопки свой урезанный попап). Список `keys` кнопки должен совпадать с тем, что она передаёт в `scs_settings.require(settings, [keys...])` сразу после получения настроек, плюс любые дополнительные ключи, которые она читает, но не требует обязательными.
- `SCS.panel/SetupParameters` больше не редактирует настройки — только проверяет/добавляет привязку общих параметров к категориям из подключённого файла ФОП (читает настройки тихо, через `get_settings_silent()`). У `SKUD.panel/SetupParameters` та же логика. У СОУЭ/СПС/CircuitsSPA такой привязки не было, поэтому их кнопки SetupParameters удалены целиком.
- Константы имён параметров/семейств по умолчанию в `scs.py` намеренно пустые строки/списки — это соглашения конкретного проекта (например, общие параметры с префиксом проекта), и их нельзя зашивать в отслеживаемые файлы. Ключевые слова классификации (коннектор, розетка, панель, стояк, ...) считаются общей лексикой и имеют разумные значения по умолчанию.
- `PlaceRouteNodes` и `RenumberAddresses`/`SyncCircuitsAndLengths` защищаются от устаревших данных: `clear_stray_address_params` очищает параметры адреса, оставшиеся на элементах, которые больше не имеют типа маршрута/стояка (например, после того как семейство устройства было выделено из общего семейства-маркера на более ранней итерации проекта), а `SyncCircuitsAndLengths` сообщает о дублирующихся адресах, а не молча их перезаписывает.

## Грабли IronPython/Revit API, уже обойдённые здесь

- `el.Name` выбрасывает ошибку неоднозначного связывания на некоторых типах элементов (в частности `Family`/`FamilySymbol`) в IronPython; используйте вместо этого `Element.Name.GetValue(el)` (см. `_safe_element_name` в `scs_settings.py`).
- Перечисление всех загруженных типоразмеров семейства категории (включая ещё не вставленные) должно идти через `FilteredElementCollector(doc).OfClass(Family)` → `family.GetFamilySymbolIds()`, а не через `FilteredElementCollector(doc).OfCategory(...).OfClass(FamilySymbol)`, который может пропустить невставленные типы.
- Окна настроек на WPF: никогда не ставьте `Topmost` на окно, которое само открывает другое WPF-окно (например, `forms.SelectFromList`) — дочернее окно застревает позади него, и его невозможно вывести на передний план.
- Это Python 2 (IronPython): `unicode(...)` и литералы `u"..."` используются по всему коду намеренно; не «модернизируйте» их под обработку строк Python 3.
- `str.format` в IronPython не принимает точность для `int` (`u"{:.0f}".format(1920)` падает с «Precision not allowed in integer format specifier», хотя CPython это пропускает). Перед форматированием через `{:.Nf}` приводите значение к `float(...)` — например, результаты `_as_int` или `Parameter.AsInteger()`.

## Notes.panel («Заметки по проекту»)

Библиотека — отдельный пакет `lib/pnotes/` (не `lib/lowlife/`); заметки хранятся в общей Google Таблице через веб-приложение Apps Script (`docs/notes/Code.gs`, установка — `docs/notes-panel.md`). Адрес и токен — у каждого пользователя свои (`%APPDATA%\pyRevit\ProjectNotes\config.json`, вводятся в окне «Настройка»); `config.json` в корне репозитория не коммитить (он в `.gitignore`, пустой образец — `config.example.json`). Напоминания при открытии модели дописаны в конец `hooks/doc-opened.py` в отдельном `try/except`, чтобы не ломать существующую логику хука и открытие модели.

Окна не ждут сеть перед открытием: «Сводка»/«Новая заметка»/«Настройка» стартуют с сохранённых копий настроек (`core.get_settings_fast()`) и заметок (`core.cached_notes()`), а каждый запрос к таблице при открытом окне идёт через `ui.in_background(window, work, done)` — `work` выполняется в фоновом потоке (только сеть и файлы, никогда Revit API), `done` — в потоке окна через `Dispatcher`; при закрытии окна запросы обрываются (`core.abort_requests()`), потоки дожидаются. Не возвращайте синхронный `core.call(...)` перед `ShowDialog()`. Сохранение новой заметки не ждёт вовсе: окно кладёт её в очередь (`core.queue_note`) и закрывается, а `core.send_queue_detached()` отправляет очередь в потоке, который живёт дольше скрипта кнопки, — поэтому у NewNote постоянный движок pyRevit (`engine: persistent` в `bundle.yaml` и `__persistentengine__` в `script.py`); такие запросы идут с `track=False`, чтобы закрытие окна их не обрывало. Любая запись в `queue.json` — под `core._QueueLock` (блокировка на весь AppDomain: у движка каждой кнопки своя копия модуля), а `flush_queue` убирает из очереди только реально отправленные заметки. Действия в сводке (статус, правка, ответ) оптимистичные: `SummaryWindow._apply` сразу меняет список, отправляет в фоне, при ошибке откатывает, не даёт закрыть окно, пока отправка не закончилась, и накладывает свои изменения поверх загрузки из таблицы, начатой до их сохранения. `core.call` один раз повторяет запрос при временном сбое (обрыв связи, 5xx/429, HTML-страница ошибки) — все действия Code.gs безопасно повторять (`add` отсеивает дубли по id); новые действия должны оставаться такими же.

Возможный следующий шаг (не сделан — пользователь пока решил не делать): немодальные «Сводка»/«Новая заметка», чтобы при открытом окне можно было работать в Revit. Что для этого нужно: `Show()` вместо `ShowDialog()` и постоянный движок pyRevit для этих кнопок (`persistent` в `bundle.yaml`), иначе обработчики окна умирают вместе со скриптом кнопки; каждый вызов Revit API из окна («Показать» в сводке — выделить/показать элементы, «Перейти на вид»; чтение активного вида и выделения для новой заметки — его лучше брать в момент «Сохранить», а не при открытии окна) — только через `ExternalEvent`; одно окно на кнопку (повторное нажатие выводит открытое вперёд); сводка должна переживать закрытие своей модели или переключение на другой документ (действия сообщают, что модели нет, а не падают). «Настройка» читает «Сведения о проекте» напрямую — её оставить модальной.

Кнопка «Обратная связь» (`_Themes.panel/Feedback`, `lib/pnotes/feedback.py`) использует ту же HTTP-обвязку, но пишет в *отдельную* таблицу автора (`docs/feedback/Code.gs`, только дописывание — прочитать через него ничего нельзя; установка — `docs/feedback-panel.md`). Адрес её веб-приложения — единственное намеренно закоммиченное значение (`FEEDBACK_URL`): до него должен достучаться любой пользователь без настройки; токена нет. Списки панелей/кнопок строятся по папкам расширения через `lowlife.ribbon_catalog`, новые кнопки появляются в них сами.

## Иконки

Иконки кнопок — это PNG 96×96, сгенерированные программно через Pillow, а не нарисованные вручную или взятые откуда-то ещё, в фирменной палитре логотипа, в двух версиях на кнопку: `icon.png` для светлой темы Revit (светло-серый скруглённый фон, почти чёрный линейный рисунок) и `icon.dark.png` для тёмной (чёрный фон, белый рисунок) — pyRevit сам берёт `icon.dark.png`, когда в Revit включена тёмная тема. В обеих — оранжевый акцент логотипа (`#F08C28`; красный — только у кнопок удаления). Набор делает `docs/brand/restyle_icons.py` из иконок, нарисованных в прежнем стиле (светлый фон, синие линии): меняется только палитра, рисунки те же; кнопки, у которых уже есть `icon.dark.png`, скрипт пропускает, так что его можно запускать повторно. Для новой кнопки (или чтобы заменить иконку, рисунок которой не соответствует действию кнопки): добавьте функцию рисования в `docs/brand/draw_icons.py` (рисует в старой светлой/синей палитре) и зарегистрируйте её в `ICONS` — запуск скрипта запишет `icon.png`, удалит устаревший `icon.dark.png` и вызовет `restyle_icons.py`, который сделает обе версии. Рисунок должен показывать то, что кнопка делает (например, цепи шлейфов — панель и замкнутый шлейф с устройствами, а не значок адреса «F1.2»; диагностика — предмет под лупой, а не просто галочка).

Фирменная графика — в `docs/brand/`: логотип — монограмма «⅃Γ» (белая зеркальная L и оранжевая перевёрнутая L на чёрном скруглённом квадрате), её вместе с `icon.png`/`logo.png` кнопки «О программе» генерирует `docs/brand/make_brand.py`. Название (`lowlife-wordmark-source.png`) — авторская графика пользователя: буквы оставлять ровно в том положении, как нарисованы (перевёрнутые/повёрнутые буквы — задумка); скрипт её только обрезает и чистит для README. В окне «О программе» название набрано шрифтом, а не картинкой: `about.WORDMARK_LETTERS` — буквы, их преобразования и признак акцента (отражённая L, o, w, та же отражённая L, повёрнутая на 180°, = «Γ» оранжевым, как в монограмме, i, заглавная F, повёрнутая на 135° по часовой, e), `wordmark_wpf.build_image()` собирает из контуров букв шрифта WPF-`DrawingImage` (Century Gothic Bold, при отсутствии — Segoe UI). `make_brand.py` так же красит «Γ» в графике для README в оранжевый (только цвет, формы не трогает). Первая панель ленты (`_Themes.panel`, заголовок «LowLife») начинается с кнопки «О программе»; `_Themes.panel` нет в `panel_themes.THEMES`, поэтому она видна при любой теме.
