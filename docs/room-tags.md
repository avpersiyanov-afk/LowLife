# Марки помещений из связи (RoomTags)

Кнопка `ToolsRooms.panel/RoomTags` («Марки помещений»). Помещения (Room)
живут в связанной модели АР, а марки нужны в нашем документе на активном
плане. Логика — в `lib/lowlife/room_tags.py`, скрипт кнопки тонкий.

## Что делает за один запуск

Работает по активному виду (`ViewPlan` — план этажа/потолочный;
на других видах кнопка сообщает и выходит). **Shift+клик** (`EXEC_PARAMS.config_mode`)
вместо активного вида открывает список всех планов проекта (без шаблонов)
с множественным выбором — марки обновляются сразу на всех выбранных
планах в одной транзакции.

Пользователь выбирает типоразмер марки из списка — это все загруженные
типоразмеры категории «Марки помещений» (перечисляются через
`Family.GetFamilySymbolIds`, чтобы не потерять ещё не вставленные — см.
грабли в `CLAUDE.md`).

Затем в одной транзакции:

1. **Удаляет марки, которые показывают «?».** Раньше такую марку пытались
   починить на месте (переставить голову, при необходимости пересоздать
   с переносом головы/полки) — код был сложнее, а разница с «просто
   удалить и дать шагу 3 поставить новую с верной головой» на практике
   не оправдывала себя. Упрощено 2026-09-17. Маркой-«?» считается любая
   из:
   - `_resolve_tag_room` вернул `dead` — `TaggedRoomId` не разрешается в
     Room (связь удалена из проекта либо помещение в связи исчезло);
   - `RoomTag.IsOrphaned == True`;
   - `_room_ok(room)` == False — это не Room (id занял другой элемент
     после пересоздания помещений), либо Room не размещён (нет
     `Location`) / не окружён (`Area == 0`);
   - **точка привязки марки вышла за границы её же помещения**
     (`_tag_anchor_in_room`, любое расстояние) — известная грабля Revit:
     такая марка показывает «?», сам Revit её не пересчитывает (например,
     АР подрезал контур помещения). Точка привязки — это `tag.Location.Point`
     (`_tag_anchor`), **не** `TagHeadPosition`: при наличии выноски голова
     (текстовый пузырь) и точка привязки расходятся — голова может
     визуально лежать внутри помещения (выноска тянется туда обратно),
     пока сама точка привязки уже снаружи. Проверка по `TagHeadPosition`
     держалась в коде до 2026-09-17 и именно поэтому не ловила такие
     случаи вовсе — марка с выноской так и оставалась «?» после любого
     количества перезапусков кнопки; поймано диагностической кнопкой
     `DiagnoseRoomTag` (см. ниже) по жалобе пользователя со скриншотом.
     Раньше (до первого фикса 2026-09-17) здесь ещё стоял допуск в
     1000 мм от габаритного бокса помещения (`_HEAD_ESCAPE_TOL_MM`) — тоже
     убран, расстояние точки привязки от помещения роли не играет.

   Для разбора конкретной зависшей марки без починки на месте есть
   `ToolsRooms.panel/DiagnoseRoomTag` (не меняет модель, только читает и
   печатает `room_tags.diagnose_tag(doc, tag)` для выделенной марки —
   резолв `TaggedRoomId`, площадь/точку помещения, `Location.Point` и
   `TagHeadPosition` самой марки, локальные координаты и результат
   `IsPointInRoom`).

   (Была ещё эвристика «под головой марки в связи лежит другое помещение,
   чем то, на которое она ссылается» — но она давала ложные срабатывания
   на нормальных марках и переставляла их на случайно найденное соседнее
   помещение, из-за чего исходное оставалось без марки и получало вторую
   от шага 3. Убрана 2026-09-11 вместе с `_find_link_room_at`/
   `_recreate_stale_tag`, которые больше нигде не нужны после отказа от
   починки на месте.)

   Список марок вида собирается двумя коллекторами — вид-скоуп
   `FilteredElementCollector(doc, view.Id)` **плюс** общий сбор с
   фильтром `OwnerViewId == view.Id` (осиротевшие марки из вид-скоупа
   иногда выпадают), с дедупликацией по `Id`.

   `link_unloaded` (связь, на которую смотрит марка, сейчас выгружена) —
   **не трогаем**: нельзя понять, жива ли привязка. Считается отдельно
   (`stats["link_unloaded"]`).
2. **Приводит типоразмер** всех оставшихся (не-«?») марок помещений на
   виде к выбранному (единый вид марок на листе).
3. **Добавляет недостающие марки** для помещений связей, которые
   попадают на уровень вида (отметка центра в пределах
   `_LEVEL_TOL_MM` = 1500 мм от отметки уровня вида) и в область подрезки
   (если она включена), но ещё не помечены — включая освобождённые
   шагом 1.

Марки для помещений связи создаются единственным доступным способом —
`doc.Create.NewRoomTag(LinkElementId(link.Id, room.Id), UV, view.Id)`
(аналога `IndependentTag.Create` для помещений в API нет).

## Обход грабли с подложкой

При включённой подложке Revit отказывается ставить марку помещения
(«point is not in a room») либо сажает её на помещение с подложки. Перед
работой кнопка снимает подложку активного вида
(`SetUnderlayBaseLevel(InvalidElementId)`), а в блоке `finally`
возвращает прежние базовый/верхний уровни подложки.

## Устойчивость к ошибкам на отдельных марках/помещениях

Обработка каждой марки (в п. 1) и каждого помещения связи (в п. 3) — в
своём `try/except`; падение на одной не прерывает проход по остальным и
считается в `stats["errors"]`. Это важно, потому что весь проход по виду
идёт в одной транзакции — необработанное исключение из `run()` откатило
бы транзакцию целиком, отменив уже сделанные исправления, и молча выглядело
бы как «кнопка ничего не поправила». Скрипт кнопки дополнительно оборачивает
сам вызов `room_tags.run` в `try/except`: если что-то всё же вылетит
исключением наружу, покажет `forms.alert` с трассировкой вместо тихого
отката; если `errors` в статистике ненулевые — покажет их количество.

## Итог

В остальном кнопка отрабатывает молча — окна-отчёта нет. `room_tags.run`
всё же возвращает словарь-статистику (`added`, `deleted`, `retyped`,
`already`, `link_unloaded`, `orphan_unresolved`, `out_of_view`,
`room_no_point`, `errors`) на случай, если сводка снова понадобится.
