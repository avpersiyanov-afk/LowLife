# SCS.panel — requirements for families and parameters

> The manual circuit button «SCS circuits» physically lives on a separate panel `CircuitsSCS.panel` («Electrical circuits» → SCS) and doesn't use the SCS settings at all (the «Wire» parameter is a built-in Revit parameter with no project-specific name) — see the «SCS circuits» section at the end of this file.

Five buttons on the `SCS` panel share one settings file (see `lib/README.md` → `scs_settings.py`), but EACH shows its own scoped-down window on Shift+click — only the fields it uses itself (there's no shared form for the whole panel any more). The first four are a common ecosystem of route nodes (panels/risers/route); the fifth (the riser diagram) doesn't look at route nodes at all, only at devices/panels through the circuits already set up (see item 4 below). No parameter/family names are stored in the repository — everything is entered in the particular button's settings window on the first run and saved locally, in the shared file `%APPDATA%\pyRevit\LowLifeSCS_settings.json`.

Devices (outlets, sensors, etc.) **don't count** as a separate insertion point/marker — the route line is brought right up to the device in plan (regardless of height), and RenumberAddresses finds the nearest already addressed route node for a panel/device by XY itself.

0. **Bind parameters** (`SetupParameters`, formerly «SCS parameters») — no longer shows a window for setting values (that's now the Shift+click on each working button below); it checks that the parameters are bound to the right categories in the project and adds missing bindings from the connected shared parameters file. Run it first — when connecting the plugin to a new project/shared parameters file, once the needed fields have been filled in through the Shift+click of the corresponding buttons.
1. **Route nodes** (`PlaceRouteNodes`) — places panels/route nodes/risers at the points of a cable route.
2. **Node addresses** (`RenumberAddresses`) — numbers the addresses of these nodes per floor, from panels/risers, and along the way finds and writes the nearest addressed route node for target panels/devices.
3. **Circuit sync** (`SyncCircuitsAndLengths`, «Circuit length» on the ribbon) — calculates cable lengths and the numbers/routes of electrical circuits from the already addressed nodes and the nearest node already found.
4. **Riser diagram** (`BuildScsSchematic`) — independent of 1-3: it finds devices itself through the same circuits/panels as «Circuit sync» (`lib/scs.py:collect_target_panel_devices`) and builds a drafting view with frames by floor/room (the device and the panel — each its own schematic family with a tag) and its own independent coloured bus per panel: its own horizontal collector on each of its floors (only its own device branches), its own vertical riser through all its floors, all in that panel's colour (collectors and risers of different panels on one floor are spread apart in height/X so they don't overlap). It doesn't need «Route nodes»/«Node addresses» — it can be run right after «SCS parameters» as soon as the circuits/panels are set up. Details — in `lib/README.md` → `scs_schematic.py`.

The natural run order of the first three is exactly this order (each next one uses the previous one's result); the fourth («Riser diagram») doesn't depend on them and can be run at any time after «SCS parameters».

## 0. SCS parameters (SetupParameters)

Reads the same text settings (parameter names) as the other three buttons and checks, for each parameter, whether it is bound in the project to the right category (Generic Models / devices-panels / electrical circuits, instance or type — depending on the parameter).

- If the parameter is already bound everywhere it should be — does nothing.
- If the parameter's definition **is** in the shared parameters file connected to Revit (Manage → Shared Parameters) but isn't bound to the right category — adds the binding automatically.
- If the parameter's definition is in **neither** the project nor the shared parameters file — it creates nothing and makes nothing up: it reports a list of such parameters so you can add them to the file by hand and run the button again.
- The «Load Name» parameter is usually an existing native Revit MEP parameter, not from the shared parameters file, so it's only mentioned in the report; its binding isn't checked/created.
- If no shared parameters file is connected to Revit at all — the button stops with a message saying so.

A detailed report (what is bound, what was added, what is missing) is in the pyRevit output window that opens after the run.

## 1. Route nodes (PlaceRouteNodes)

### The route segment family

- Category — **Generic Models**, a **line-based** instance (`LocationCurve`).
- The family name contains the marker given in the **«Route segment family filter»** field (for example «Участок трассы»).
- For automatic detection of the installation type, the segment's type name must contain «в трубе» → «Труба» (conduit), «в лотке» → «Лоток» (tray), «в трубе... открыто» → «Труба открыто» (open conduit) (built into the logic, not configurable through the settings window). This value is written to the route node adjoining this segment, but **not here** — by the «Node addresses» button (item 2): at a joint of segments with different installation methods you need to know the direction «towards the panel», otherwise at a conduit/tray joint the type could be detected wrongly/unpredictably (see the details in item 2).
- (Optional) a numeric elevation/offset parameter — name(s), comma-separated, in the «Possible elevation parameter names» field.

### Panels and risers (recognising route points)

- Looked for in the categories: Communication Devices, Electrical Equipment, Electrical Fixtures, Data Devices.
- A **point-based** instance (`LocationPoint`).
- The kind (panel/riser) — by keywords in the family/type name (the «Panel keywords»/«Riser keywords» fields + exclusion words). If a point fits several kinds at once, the priority is: riser > panel > route node.
- Devices (outlets, sensors, etc.) aren't recognised here and don't get an insertion point of their own — they don't need one, see section 3.
- A riser can additionally be marked with a **typical annotation** of the «Generic Annotations» category (`OST_GenericAnnotation`, with an up/down arrow) instead of a real device — recognised by a **separate** field «Riser annotation keywords» (not related to «Riser keywords» — the annotation type name usually doesn't contain the word «стояк», for example «Стрелка опуска и подъёма»). The field is optional: if left empty, annotations aren't searched for at all. An annotation has no height of its own in the model (it's only visible in the view), so the node is placed at its point on the plan (X/Y) at a nominal height of 3000 mm above the active view's level; the placement level is the level of that same view (an annotation has no «Level» parameter, unlike a real riser device).

### Types to place (panel / riser / route)

- Types of the **Generic Models** category, **point-based, unhosted** (standalone — Revit lets you place them at any point right away). The list to choose from is taken from **all types loaded in the project** for this category, even if no instance has been placed yet — with the family name and type name.
- Each must have (otherwise the value is quietly not written):
  - a text parameter «Cable installation type» (for panels/risers the value from «Cable installation type for panels and risers» is written right here, in PlaceRouteNodes; for a route node — not here but by the «Node addresses» button, see item 2, since at a joint of different installation methods you need to know the direction towards the panel);
  - a text parameter «Route type» — «The «Route type» value (not for risers)» for panel/route, and a separate «The «Route type» value for risers» (for example «Горизонтальный» and «Вертикальный» — horizontal and vertical — respectively);
  - (if you use it) a numeric elevation parameter — one of the names from the «Possible elevation parameter names» list.

### A re-run doesn't create copies

The button places nodes only along elements of the **active view** — and looks for existing elements of the chosen types only in that view too: if there's already a marker of the right type (panel/route/riser) at a point, the point is **skipped entirely** — nothing is created and nothing is updated in the existing element. The match is checked by **real distance** (within ~30 mm) by simply going through all markers already in the view — each existing element can be used only once per run. So running the button again on the same view (for example after adding new route segments) is safe — no new element appears where things are already marked, only missing nodes are added. If you run the button from another view where the same route is visible, it won't check against the markers placed from the first view (its de-duplication is limited to the active view), so it makes sense to always run it from the same view for a given route.

## 2. Node addresses (RenumberAddresses)

### What's needed in addition to item 1

- **The type for riser points** — the same type chosen for risers in item 1 (the field is shared by both buttons). Risers and panels are the «roots» of the numbering: the traversal starts from them.
- Two text instance parameters **on the «route node» type**:
  - «The «Node address» parameter» — the calculated address is written into it. For ordinary route nodes — of the form `F1.3` (the floor code + a sequence number); for panels — `F1.P1`, `F1.P2`... (a counter of their own per floor, prefix `P`); for risers — `F1.R1`, `F1.R2`... (prefix `R`). The address of a panel/riser is always recalculated on every run.
  - «The «Previous address» parameter» — the address of the parent node in the traversal tree; for the node nearest to a panel/riser, this is the new address of the panel/riser itself (`F1.P1`, etc.), not whatever was typed into it by hand. It may contain several addresses separated by commas: besides the parent it also gets any physical neighbour on the route the traversal tree didn't reach directly (relevant on a floor with several panels — one physical network is split into subtrees, one per panel, with no link between them; the extra address in the parameter restores that link for «Circuit length» without touching the numbering itself).
- The floor code is taken from the level name (or the view name if there's no level): the words «этаж»/«цоколь» (floor/basement) followed by a number are looked for, otherwise the first number in the name. If the project has several levels with **the same name** but different elevations (for example two «Этаж -1» levels in different sections/buildings), they get different codes — the lowest by elevation among the same-named ones gets the base code (`F-1`), the next by height `F-1.1`, the next `F-1.2`, and so on. Otherwise both levels would get the same code and, as a result, the same node addresses, and SyncCircuitsAndLengths couldn't tell which of the two floors an address belongs to.

### How the root is chosen

Panels have priority: if among the panels in the view there's at least one **within the area where there actually are route nodes** (plus a 20-metre margin — `ROOT_SEARCH_MARGIN_MM` in the script), only such panels become **main** roots. Panels farther from this area (even if they're real, just at the other end of the building/project) aren't taken as roots — otherwise the fallback search for the nearest node (with no distance limit) could «stick» such a panel to a randomly nearest node of a completely different network. Only if there's **no** panel within the area do risers become the main roots (by the same distance rule). From each chosen root the nearest route node on the same line is looked for (or simply the nearest one if the line has no nodes) — **on every** line physically coming to the panel/riser, not just on one «nearest» one: if several separate route segments physically converge on one panel (a typical case — risers on the left and right of the building, both leading to one panel), it is attached to all such segments at once, not only to the nearest of them. Otherwise the segment that didn't win the «nearest» comparison would be left with no link to the panel at all — its first node went to an anonymous local root, and the devices behind it found no path to the panel in «Circuit length», although the addressing itself looked completely correct (addresses and «Previous address» were assigned normally — they just led to a separate tree not connected to the panel).

Then the **shortest path to the root** is found for each node (Dijkstra's algorithm, the weight is the real distance between nodes, not the number of graph steps) — this is what defines each node's «previous address». The order of the numbering itself is a depth-first traversal (DFS) over the resulting tree: one branch gets consecutive numbers from start to end, and only then is the next branch numbered (numbers don't alternate between neighbouring branches).

**Risers on a floor with a panel aren't discarded entirely.** If a floor has a panel but also a riser physically leading along ITS OWN branch, not connected by lines to the panel's network (for example a second riser serving another part of the floor), such a riser doesn't become a root competing on equal terms with the panel (otherwise it would risk «pulling over» through Dijkstra a part of the network already connected to the panel — Dijkstra always chooses the root nearest by real distance, not «the panel wins by default»); instead it is used as a fallback root **only** for nodes the traversal from the panel physically didn't reach. So a separate branch gets addresses and a «Previous address» referring to a real riser instead of staying cut off from the panel's network (which used to mean «Circuit length» found no path for the devices behind such a riser, although their «Nearest route node» was written correctly). Nodes connected to no root at all — neither a panel nor a fallback riser (a separate branch with no panel/riser nearby) — still get an address, just without a «previous address» on the very first node of such a branch.

The button always renumbers **all** route nodes in the active view from scratch (no mode choice) — addresses and «Nearest route node» are recalculated and overwritten on every run, even if a value was written before.

### The route node's cable installation type

Also determined here (not in PlaceRouteNodes) — by the «Cable installation type» parameter of the segment **towards the parent** (in the direction of the panel/riser), not from the node further on to the devices. The direction is only known after the tree is built (see «How the root is chosen» above), so earlier (when this was determined in PlaceRouteNodes without any notion of direction) a node at a joint of two segments with different installation methods (for example conduit turning into tray) could unpredictably get either of the two types — and the length in conduit/in tray in SyncCircuitsAndLengths was calculated wrongly.

The point of using the parent direction: the installation method must change exactly at the joint, not later. If node B stands at the joint «conduit(A→B) → tray(B→...)», segment A→B is still in conduit, and the segment from B onwards is already in tray; SyncCircuitsAndLengths takes each segment's installation method from the parameter of the node it **leaves from** (closer to the panel) — so the type on node B, equal to the type of the segment towards A (conduit), gives the right result for segment A→B, and the next node's type — for the segment after the joint. The root node (nearest to the panel/riser, it has no parent in the tree) takes any adjoining segment.

### Clearing foreign addresses

Before collecting nodes, both buttons (RenumberAddresses and SyncCircuitsAndLengths) automatically clear the «Node address»/«Previous address» parameters on any elements that are NOT the chosen route node/riser type — for example on devices left over from earlier runs (when there was no split into panel/device/route yet) or filled in by hand. Otherwise a path could accidentally go through such a «foreign» address instead of a real route node. The number of cleared elements is shown in the final summary.

### The nearest route node for panels and devices

Right after numbering the addresses, the same button (here rather than in SyncCircuitsAndLengths — it's more logical to calculate it straight away while there are fresh addresses for it) finds the target panels (`OST_ElectricalEquipment` by workset) and devices (the first non-excluded device in each circuit of each target panel), calculates and **always overwrites** the text parameter «Nearest route node» — the address of the nearest node **by XY only** (ignoring Z): a panel or device is brought to the route line right in plan, and the difference in connection height (for example an outlet at 300 mm) mustn't override the right choice of node.

## 3. Circuit sync (SyncCircuitsAndLengths)

It no longer works with geometry but with the addresses and the «Nearest route node» parameter written in step 2, and with the electrical circuits (`OST_ElectricalCircuit`) of the project's real panels.

### Target panels

- Looked for among `OST_ElectricalEquipment` by **workset**: the workset name must contain the keyword from the «Target panel workset keyword» field (for example «ВОС»).
- The panel must have the text parameter «The «Nearest route node» parameter» — the address of the node the path to the devices starts from (written by the «Node addresses» button, see above; if it's missing, the panel is simply skipped).

### Circuits and devices

- The circuit must be connected to a target panel (the circuit's built-in «Panel» = the panel's `Name`) — that's how circuits are grouped by panel.
- «The circuit «Name» parameter» — the circuit kind is determined by it: it contains a word from «оптическая»/«UTP»/«силовая» (fibre/UTP/power; the fields are configurable).
- The first non-excluded device of the circuit (other than the panel itself) is the one the path is searched to. Devices whose family name contains a word from «Spare port keywords» aren't counted.
- The device has a «Device address» parameter and a «Designation» — they make up a «load name» of the form `Designation.Address`. «Designation» is bound by the «Bind parameters» button as a **type** parameter (SetupParameters checks the binding on the type), but if it already existed in the project as an **instance** parameter, the type won't have a value, and the button then reads the same parameter name straight from the device instance (the type is checked first, and if empty — the instance).
- The nearest route node for the device must also be written already (by the «Node addresses» button); if it isn't, the path for that circuit isn't calculated («No node on the device» in the final summary).

### What is written

- On the circuit: the wire length (total/in tray/in conduit — with safety factors from the settings), the installation method (text by templates with `{}` for metres), the circuit number (`FO-N`/`PWR-N` — only for fibre/power circuits of the right workset), the circuit route (node addresses joined with `->`), the load name (except for fibre circuits).
- On each route node along the circuit's path: the «Circuit list» parameter — text with the list of names of circuits passing through this node and a summary of the number of fibre/UTP circuits.

### Diagnostics

If no path to the panel is found for a circuit (the graph is broken — for example a route node isn't connected to its neighbours), this doesn't raise an error — the circuit is skipped, and the pyRevit output window prints exactly which nodes the break is between (the nearest pair of points on either side of the break). There, too — a list of circuits with a «Previous address» parameter referring to a non-existent address (a typo or a node not numbered yet).

## 4. Riser diagram (BuildScsSchematic)

It doesn't depend on route nodes (items 1-2) at all — it uses only the same circuits/panels as «Circuit sync» (item 3): target panels by workset, devices by the circuit «Panel» parameter. It can be run right after «SCS parameters», without «Route nodes»/«Node addresses».

### What is drawn

- A drafting view (created with the name from the settings; on re-runs the same view is updated) with frames by floor (label «Этаж N (elevation)») and room (by the room parameter — if empty, it is looked up in the linked architectural model by the device/panel point and written in). Rooms on each floor go from left to right in the same order as on the plan (by the real minimum X of the room's devices in the model, separately on each floor) — not by room number or name, as in the CCTV/fire alarm riser diagram. If the settings have a «Maximum width of a row of rooms on a floor, mm» (empty by default — no limit), a room that no longer fits in the current row wraps to a new row BELOW (like word wrap — the room order doesn't change, only how many rows it's split into); the floor frame stretches in height to fit all rows automatically. This keeps the sheet from getting very wide when a floor has many rooms. Every other row is mirrored (the label and node tag at the bottom, the line to the bus/panel from the node's top edge): neighbouring rows converge with their lines into one shared gap between them instead of crossing the neighbouring row's labels with their lines. The view template is unconditionally removed on every run (SCS, unlike CCTV, has no template setting) — if the project has a default template for new drafting views, it could hide the just-created Line Styles of the bus/backbone lines (the lines themselves are created in the model normally, they're just not visible in the view).
- Each device and each panel is its own schematic family (category `OST_DetailComponents`) with a tag above it (one tag type for the whole diagram, in the settings, category `OST_DetailComponentTags`; the tag reads «Designation»/«Address» from the schematic family itself through its label fields). Which schematic family to place is decided through **categories**, as in the CCTV riser diagram: the settings have a list of categories (for example «Розетка», «Шкаф» — outlet, cabinet), and for each separately — the schematic family to place and the real model device/panel types belonging to it (matched by the exact type ElementId, not by keywords). A device/panel whose real type isn't mapped to any category doesn't get onto the diagram (report: «Not placed»). The button's report also always prints a «Category mapping» section — for each configured category: which schematic family it is assigned and how many (and which real types of) devices actually got into it — if a category got 0 devices or several categories unexpectedly point to the same schematic family, it's visible in the report right away, no need to guess from the resulting diagram.
- Bus lines: **each panel has its own independent bus** — its own horizontal collector on each floor where the panel has a device (collecting only its own device branches, not shared with other panels), its own vertical riser to the left of the room frames through all its floors. Collectors of different panels on one floor are spread apart in height (the next panel farther from the frame, always exactly 4 mm — counted over the panels actually present on that floor rather than by their number in the whole diagram: if a panel has no devices on a particular floor, its «place» isn't skipped as an empty gap), risers of different panels — in X (the next panel to the left) — nothing overlaps. Bus lines aren't edited by hand — they're redrawn on every run (they're fully derived from the device positions already calculated, so there's no point diffing them).
- **A panel's branches, collector and riser are coloured in its own colour** (its own Line Style, created automatically from the panel name — «СКС схема — <panel name>», no settings) — the colour shows which device goes to which cabinet, even if lines of different panels visually cross on the diagram.
- The offset between the room frame boundary (not `level_y` itself — the room frame already goes 10 mm below it, otherwise the line would be drawn over/inside it) and the first cable line, and the margin between the deepest cable line and the floor frame's bottom boundary, are the same number, 8 mm (not two different values picked by eye). Each floor frame stretches down automatically exactly enough to fit all collector lines with this margin underneath (even in the worst case — if all panels of the diagram ended up on one floor), and if the diagram has at least one backbone link, also its drop row (always 4 mm farther from the floor than the deepest device bus), without going past the frame's bottom boundary.
- The same rule (8 mm from the boundary) applies horizontally too: a panel's first riser stands 8 mm to the left (farther from the rooms) of the floor frame's first line, not exactly on it; the last riser/backbone track — 8 mm farther from the floor label corridor, not outside the frame already drawn. If the risers and tracks don't fit in the corridor's usual width, the corridor automatically widens to the left exactly enough to fit them with this margin (the same principle as the room for buses, only horizontally) — and the floor label and the line separating it move further left along with it rather than staying put: the label has its own separate corridor of constant width, which simply shifts as a whole after the grown riser/track corridor rather than «stretching» with it.
- **Cabinet-to-cabinet backbone links** (for example a fibre line between panels) — defined as an electrical circuit whose target is another target panel instead of a device. Such a line leaves not from the cabinet's device bus but from **the cabinet's own node**, with a separate drop at a visible distance from the vertical branch of the same node's device bus (otherwise the transition would visually coincide with the cabinet's device bus and read as its «continuation» rather than a separate link) — down to its own row (exactly the same 4 mm farther from the floor as between any two neighbouring device bus lines — no separate larger gap), then horizontally to **its own separate vertical track**, to the left (farther from the frames) of the risers of ALL panels, the same 8 mm after the last of them (not a separate larger gap, as it used to be), and a vertical stretch along the track (it can be long — for panels on floors far apart this is the real backbone length, not an error). If several backbone links form a CHAIN (cabinet A — cabinet B — cabinet C and so on, when both A and C are linked to B), the whole chain has **one shared track**, rather than a separate track for each pair: otherwise neighbouring tracks would stand almost against each other and visually merge into something like a «box» instead of one clear line running from cabinet to cabinet along the track according to the electrical circuit. A shared fixed **bright and bold** style (not the colour of one of the panels — the link doesn't belong to only one of them; not grey or thin — so it definitely isn't lost among ordinary bus lines). A panel whose only connections are such backbones (without a single ordinary device) still gets onto the diagram — otherwise there'd be nothing to run the backbones from.
- A node tag (the address/designation above the schematic family), if the node moved between runs (for example because of changes further left on the diagram), is placed again at the new spot rather than just moved — that's more reliable.

### A re-run

As with the CCTV riser diagram: the previous run's layout is kept in a service parameter of the view itself (JSON) — only the floor/room/device where something actually changed (by the set of device `UniqueId`s in a room) is updated; the rest stays as it was, with the same elements. Neighbours to the right of/below the change shift to close or free up space. If the set of devices in a room didn't change but the «device category -> schematic family» mapping changed in the settings (for example a type was added/fixed for one of the categories), an existing node isn't re-created (the `UniqueId` set is the same), but its type is checked in place and changed to the current one if needed (without re-creating the instance itself).

### Settings

The `[Схема]` (diagram) section in «SCS parameters»: the diagram view name, the view's service layout parameter (on views), the room parameter (on devices/panels and on schematic families), the room number parameter in the linked model, the service parameter for the source device's UniqueId (on schematic families), the tag offset, **the maximum width of a row of rooms on a floor, mm** (see above), the node tag type and the multiline «Diagram device categories» field (one per line). After filling in the list of categories, press «Refresh the category list» — two pickers per category appear under the field:
- **the schematic family to place** — the list is limited to the «Detail Items» category (`OST_DetailComponents`), as it should be — this isn't a real device but a schematic symbol;
- **the real model device/panel types of this category** (several can be chosen at once) — the list is limited to the «Communication Devices» and «Electrical Equipment» categories (`OST_CommunicationDevices`/`OST_ElectricalEquipment`) — outlets/communication devices and target panels/cabinets; other Revit categories aren't in the list.

These fields are **optional** for the other four SCS buttons — empty ones don't stop «SCS parameters» from binding the other parameters and don't block «Route nodes»/«Node addresses»/«Circuit sync».

## SCS circuits (CircuitsSCS.panel → BuildCircuitsSCS)

Separate from the four buttons above, for a quick manual case: no addressing, you just need to connect a panel to several devices.

1. The button first shows a list of **wires** (cables) — the circuit «Wire» in Revit is a dropdown in itself (a reference to a key schedule row), but Revit doesn't let you get its whole catalog directly, so the list to choose from is collected from the values **already set on at least one electrical circuit of the document**. If no circuit in the project has a wire chosen yet, the list is empty and the button stops with a message saying so: choose a wire by hand once in the properties of any circuit (as usual, through Revit), then run the button again.
2. Then the panel is picked, then all devices (`PickObject`/`PickObjects`).
3. A separate electrical circuit of the **Data type** (fixed — SCS has no other circuit types, so the type isn't asked, unlike ACS/fire automation) connected straight to the panel is created for each device.
4. Each created circuit gets the «Wire» parameter — the one chosen in step 1.

The «Wire» parameter and its name aren't configured anywhere (it isn't a project-specific parameter but a built-in Revit one) — this button doesn't use the SCS settings at all.

A re-run doesn't reuse anything — every run creates new circuits for the newly chosen panel/devices/wire.

## Setup order

All five buttons use **the same** settings (shared, kept in one JSON file), but each has its own Shift+click with its own scoped-down window showing only the fields it needs (the fields in the shared JSON file are grouped into the `[Адресация]`/`[Цепи]`/`[Схема]`/`[Критерии панели]` sections — addressing/circuits/diagram/panel criteria; PlaceRouteNodes's fields have no prefix). A value saved through one button's Shift+click is immediately available to the others (the file is shared) — when first connecting the plugin to a project you can fill in the fields as you run the buttons you need, rather than in one form all at once; if a required field is missing for a button, it stops and tells you which button's Shift+click to fill it in through. The `[Схема]` fields aren't required for the other buttons — empty, they don't get in the way of running the first four (see item 4 above); they're required only for the «Riser diagram» itself.

## Which shared parameters to set up for your project

All the parameters below are ordinary text parameters (Text), except the ones marked otherwise, and instance parameters (except the one marked otherwise). You make up the real names yourself and enter them in the settings window — below is only what has to be on which category.

- **Generic Models** (route/riser/panel nodes — devices don't get a marker of their own in this category): «Cable installation type», «Route type», «Node address», «Previous address» (may contain several values separated by commas), «Circuit list» (multiline), and optionally a numeric elevation parameter (Length or Number).
- **Devices and panels** (Communication Devices / Electrical Fixtures / Data Devices / Electrical Equipment — real elements, not markers): «Nearest route node» — instance, on both; «Device address» — instance, only on the device; «Designation» — a **type** parameter of the device (read from the type, not from a particular instance); optionally (only for the riser diagram, item 4) «Room» — instance, on both.
- Only for the riser diagram (item 4), optional for the other buttons: **Views** — the service diagram layout parameter (text, JSON, not edited by hand); **schematic families** (the «Detail Items» category, `OST_DetailComponents` — as many families as the device categories you set in the settings, not necessarily exactly two) — «Room» (the same name as on devices/panels above) and the service parameter for the source device's UniqueId.
- **Electrical Circuits** (`OST_ElectricalCircuit`): a parameter with the panel name (compared with the target panel's `Name`), «Name» (the circuit kind is determined by it), «Circuit number», «Circuit route», «Installation method» — text; «Wire length» and its split by installation method — **numbers** (not «Length» — a ready number of metres is written, with no Revit unit conversion); «Load Name» — usually an existing native Revit MEP parameter that doesn't need to be set up separately, just check that it's writable. «Wire» (the «SCS circuits» button) is also a built-in Revit parameter; nothing needs to be set up.
- Not a parameter but a naming convention: the target panels' workset must contain the chosen keyword; segment/panel/riser families are recognised by a substring in the family or type name (configured with keywords in the settings window).
