# SKUD.panel — требования к семействам и параметрам

Кнопки на панели `SKUD` для автоматизации проекта СКУД (контроль
доступа): от расставленного на плане оборудования и заведённых цепей — до
готовых КЖ, спецификации кабеля и структурной схемы. Настройки — отдельные
от `SCS.panel` (свой JSON-файл `%APPDATA%\pyRevit\LowLifeSKUD_settings.json`,
своё окно). Ничего из имён параметров/семейств не хранится в репозитории —
всё вводится в окне настроек при первом запуске.

Естественный порядок запуска — в этом порядке (каждая следующая кнопка
использует результат предыдущей), как в `SCS.panel`:

0. **Параметры СКУД** (`SetupParameters`) — окно настроек + проверка/
   привязка параметров из ФОП. Запускать первым.
1. **Узлы трассы СКУД** (`PlaceSkudRouteNodes`) — расставляет панели/узлы
   маршрута/стояки СКУД по линиям трассы. Нужна только если есть далёкие
   устройства (см. ниже); если все устройства стоят вплотную к
   контроллерам, трассу рисовать не нужно и этот шаг пропускается.
2. **Адреса узлов СКУД** (`RenumberSkudAddresses`) — нумерует эти узлы и
   записывает контроллерам/устройствам ближайший узел маршрута.
3. **Цепи и кабели** (`AssignCircuitsAndCables`) — находит контроллеры и их
   цепи, назначает адреса подключённым устройствам, выбирает тип кабеля по
   словарю, пишет имя нагрузки, маркирует контроллеры.
4. **Длины и маркировка** (`CalcSkudLengths`) — считает длину проводника (по
   катетам рядом с контроллером, иначе по графу трассы), пишет длину в
   трубе/лотке раздельно, способ прокладки, марку устройств и список цепей
   на узлах маршрута.
5. **Помещение точек прохода** (`AssignSkudRooms`) — проставляет всем
   устройствам СКУД имя помещения из связи; по каждой точке прохода берётся
   одно (самое частое) значение и назначается всем её устройствам.
6. **Структурная схема** (`BuildSkudSchematic`) — по составу каждой точки
   прохода подбирает типовую группу деталей, вставляет её, разгруппировывает,
   переносит адреса, соединяет линиями. Повторный запуск — инкрементальная
   синхронизация (неизменные точки прохода не трогаются, изменившиеся
   перерисовываются, пропавшие удаляются). Состояние — JSON в служебном
   параметре вида. Отдельной кнопки обновления нет.

Маркировка намеренно живёт внутри кнопки длин, а не отдельной кнопкой:
марка устройства — это перенос уже известного адреса, а список цепей на
узлах собирается из пути цепи, который на этом шаге уже посчитан как
список (отдельной кнопке пришлось бы разбирать его обратно из текста
`"F1.1 -> F1.2"` в параметре «Маршрут цепи»).

## 0. Параметры СКУД (SetupParameters)

Аналогично `SetupParameters` в `SCS.panel` — проверяет привязку параметров
СКУД к нужным категориям, добавляет недостающие привязки из подключённого
файла ФОП. Ничего не выдумывает: если определения параметра нет ни в
проекте, ни в ФОП — только сообщает об этом.

## 1. Цепи и кабели (AssignCircuitsAndCables)

### Контроллеры

- Ищутся среди `OST_ElectricalEquipment`: рабочий набор содержит ключевое
  слово («Ключевое слово рабочего набора контроллеров»), **и** имя типа
  (`Symbol.Name`) содержит ключевое слово («Ключевое слово в имени типа
  контроллера»).
- У контроллера уже должен быть заполнен параметр «Адрес устройства»
  (вводится пользователем вручную при расстановке оборудования) — без него
  контроллер пропускается.

### Цепи и устройства

- У цепи — параметр «Панель» (контроллер) со значением, равным `Name`
  контроллера.
- Первое неисключённое устройство цепи (кроме самого контроллера) — то, на
  которое распространяется расчёт. Устройства, чьё имя семейства содержит
  слово из «Ключевые слова резервных портов», не берутся.

### Что записывается

- На устройство: «Адрес устройства» по маске `{адрес контроллера}.{N}`, где
  `N` — простой порядковый номер подключённого устройства в пределах одного
  контроллера (по всем цепям контроллера, без деления по типу устройства).
- На цепь: «Имя нагрузки» (`Обозначение.Адрес`, из параметра типа устройства
  «Обозначение» и записанного выше адреса), тип кабеля (параметр «Проводник»)
  — по словарю «тип устройства : тип кабеля», вводимому построчно в окне
  настроек (формат `ключевое_слово:тип_кабеля`, по одному на строку).
- На контроллер: параметр «Маркировка контроллера» = его же адрес.

## 2. Длины и маркировка (CalcSkudLengths)

### Порог "рядом с контроллером"

Прямое 3D-расстояние между контроллером и устройством сравнивается с
порогом («Порог «рядом с контроллером», м», в метрах).

- **Меньше порога** — длина считается по катетам:
  `|dx| + |dy| + |dz|`, умноженным на коэффициент запаса («Коэффициент
  запаса для расчёта по катетам»). Весь объём пишется в «Длина проводника в
  трубе» — способ прокладки всегда труба, «Длина проводника в лотке» = 0.
- **Больше порога** — длина считается по графу адресованных узлов трассы
  СКУД, **тем же алгоритмом и с той же математикой, что в `SCS.panel`**:
  A* по адресам узлов (`astar_path`), разбивка по способу прокладки
  (`calc_lengths`), вертикальная составляющая отдельно, коэффициенты
  запаса, согласованное округление (`balance_round_parts`) — всё это те же
  функции `lib/lowlife/scs_circuits.py`, а не их копии.

### Узлы трассы СКУД — свои, отдельные от СКС

Узлы СКС показывают путь до шкафа СКС, узлы СКУД — путь от устройств до
контроллера, поэтому это **разные** элементы: свои семейства панели,
маршрута и стояка, выбираемые в «Параметры СКУД» отдельно от СКС.

**Имена параметров при этом общие с СКС** (`SMNX_Сегмент_Адрес` и
остальные) — дисциплины разделяет **рабочий набор**, а не отдельные
параметры. Ключевое слово задаётся полем «Ключевое слово рабочего набора
элементов СКУД» и применяется в трёх местах:

- панели/контроллеры — иначе шкаф СКС, подходящий под похожие ключевые
  слова («панель», «шкаф»), стал бы корнем обхода для трассы СКУД;
- **сбор узлов трассы** — он идёт по всему документу, а не по активному
  виду, поэтому без фильтра узел СКС с тем же адресом (`F1.3` есть и там,
  и там) попал бы в граф СКУД и путь пошёл бы через чужую трассу;
- **очистка «чужих» адресов** — иначе запуск СКУД стирал бы адреса узлов
  СКС, и наоборот.

В сводке после запуска есть строка «Узлов чужого рабочего набора
пропущено» — если она неожиданно большая, значит рабочий набор узлов
заполнен не так, как ожидает фильтр.

Порядок для далёких устройств:

1. СКУД → **«Узлы трассы СКУД»** — расставляет узлы по линиям трассы СКУД;
2. СКУД → **«Адреса узлов СКУД»** — нумерует их и записывает контроллерам
   и устройствам «Ближайший узел маршрута»;
3. СКУД → **«Длины и маркировка»**.

### Что записывается

- «Длина проводника» (сумма трубы и лотка — то же самое число, что попадает
  и в КЖ, и в спецификацию, без отдельного пересчёта или переноса длины из
  цепи), «Длина проводника в трубе», «Длина проводника в лотке» —
  раздельно (в отличие от СКС, где труба и труба-открыто объединяются в
  один параметр).
- «Способ прокладки» — текст по шаблонам с `{}` для метров, на основе
  значений «в трубе»/«в лотке».
- «Маршрут цепи» — адреса узлов через `->` (пусто для случая "рядом с
  контроллером", т.к. там нет узлов графа).
- «Марка устройства» = значение «Адрес устройства» (перенос, без пересчёта).
- «Список цепей» на каждом узле маршрута, через который проходит хотя бы
  одна цепь (накапливается прямо во время расчёта путей — путь на этом
  шаге уже есть списком адресов).

## 3. Помещение точек прохода (AssignSkudRooms)

Как «Помещение из связи» в СПС/СОТ, но с учётом того, что устройства одной
точки прохода стоят в разных помещениях (считыватель снаружи, замок в
проёме и т.д.). Логика:

- контроллеры и их устройства собираются так же, как в «Цепи и кабели»;
- устройства контроллера разбиваются по **точкам прохода** — значению
  параметра «Номер точки прохода» (пусто у устройства → точка прохода 1);
- по каждой точке прохода берётся имя помещения для каждого устройства
  (поиск в связях — та же механика `room_info.py`), выбирается самое
  частое непустое значение и записывается **всем** устройствам точки
  прохода;
- контроллеру помещение пишется индивидуально (без большинства).

Имена параметров (куда писать «Имя (Номер)», из какого параметра Room
связи брать номер) — общие с СПС/СОТ, берутся из «Параметры помещений»
(`room_info_settings`), в настройках СКУД не дублируются.

## 4. Структурная схема (BuildSkudSchematic)

### Типовые группы деталей

Пользователь заранее собирает в проекте Revit-**группы деталей**:

- **узел-контроллер** — схемные семейства и рамка одного контроллера;
- по одной группе на каждый типовой **состав точки прохода**
  (односторонняя: считыватель + замок + кнопка выхода + геркон;
  двусторонняя: считыватель ×2 + замок + геркон; и т.д.).

Группы выбираются в «Параметры СКУД» → «Типовые группы структурной схемы»
(список показывает только группы деталей). Каждая выбранная группа должна
быть хотя бы раз размещена в проекте — её состав читается по первому
размещённому экземпляру.

### Точки прохода и подбор группы

- Устройства контроллера делятся по точкам прохода (параметр «Номер точки
  прохода», пусто → точка прохода 1).
- Для точки прохода строится **сигнатура** — мультимножество категорий её
  устройств (категория определяется точным типом семейства, см.
  `schematic_category_device_type_ids`).
- Ищется группа точки прохода с точно такой же сигнатурой. Категория
  схемных элементов внутри группы определяется по типу схемного семейства
  (`schematic_category_type_ids`).

### Что делает кнопка (инкрементальная синхронизация, как СОТ/СПС)

- находит чертёжный вид с именем `schematic_view_name` (или создаёт его),
  читает состояние схемы из JSON в параметре вида `manifest_param_name`
  (тот же приём, что `sot_layout_state`);
- узел-контроллер вставляется один раз на контроллер и
  **разгруппировывается**; схемному элементу категории «контроллер»
  пишется адрес; каждому схемному элементу пишется `UniqueId` исходного
  устройства в `schematic_source_uid_param` — постоянная связь схема↔модель;
- **единица неизменности — точка прохода.** При повторном запуске:
  - тот же набор устройств (по `UniqueId`) и та же подобранная группа →
    точка прохода **не трогается по геометрии** (ручная раскладка
    сохраняется), обновляются только «Адрес устройства» / «Марка
    устройства» на схемных элементах;
  - набор устройств или подобранная группа изменились → точка прохода
    **удаляется и рисуется заново**;
  - точка прохода пропала из модели → удаляется;
  - новая точка прохода → размещается;
  - контроллер пропал из модели → его узел и все точки прохода удаляются;
- на совпавшую точку прохода вставляется подобранная группа,
  разгруппировывается; схемные элементы сопоставляются реальным
  устройствам по категории (в пределах категории — по порядку адреса);
- **no-match** (для состава точки прохода нет группы): резервная раскладка
  — каждое устройство отдельным схемным семейством категории, плюс строка
  в отчёте с составом и просьбой создать группу;
- линии контроллер→точка прохода **пересоздаются каждый запуск** (у прямых
  коннекторов ручной маршрутизации нет), якорь — среднее положение
  фактических схемных элементов (следует за ручным перемещением);
- новое состояние пишется обратно в параметр вида.

Отдельной кнопки «обновить» нет — повторный запуск «Структурной схемы»
сам находит изменения.

## Диагностика (InspectSchematicDevices)

Отдельная кнопка на `SKUD.panel`, не часть рабочего конвейера: по выбранному
контроллеру печатает в окно вывода pyRevit все его цепи, все элементы
каждой цепи (с адресом и признаком «исключён по ключевому слову») и
итоговый список устройств, которые `BuildSkudSchematic` поставит на
структурную схему — с подсветкой дублей по `ElementId`. Используется при
отладке, если схема выглядит не так, как ожидалось (лишние/пропущенные
устройства у контроллера).

## Какие общие параметры (ФОП) нужно завести под свой проект

Аналогично `docs/scs-panel.md` — все текстовые (кроме отдельно помеченных),
экземпляра (кроме отдельно помеченного). Реальные имена придумываются
пользователем и вписываются в окно настроек.

- **Обобщённые модели** (узлы маршрута/стояков СКУД): «Адрес узла»,
  «Предыдущий адрес», «Тип прокладки кабеля», «Список цепей»
  (многострочный) — это **те же самые параметры**, что использует СКС,
  заводить отдельные не нужно. Разделяет дисциплины рабочий набор;
  отдельными у СКУД остаются только id типов семейств (свои узлы).
- **Устройства и контроллеры** (Коммуникационные устройства /
  Электротехнические изделия / Датчики данных / Электрооборудование):
  «Ближайший узел маршрута» — экземпляра, у обоих; «Адрес устройства» —
  экземпляра; «Обозначение» — типа устройства; «Маркировка контроллера» —
  экземпляра контроллера; «Марка устройства» — экземпляра устройства;
  «Номер точки прохода» — экземпляра устройства (необязательный: пусто →
  у контроллера одна точка прохода; 1/2/… — если к контроллеру подключено
  несколько точек прохода); имя помещения («Имя (Номер)») — экземпляра,
  у всех устройств и контроллеров, задаётся в «Параметры помещений».
- **Схемные семейства** (Detail Items структурной схемы): служебный
  текстовый параметр `schematic_source_uid_param` — экземпляра, туда
  `BuildSkudSchematic` пишет `UniqueId` исходного устройства (связь
  схема↔модель для инкрементальной синхронизации). Аналог
  `device_uid_param_name` у СОТ.
- **Электрические цепи** (`OST_ElectricalCircuit`): «Панель» (контроллер),
  «Проводник» (тип кабеля), «Маршрут цепи», «Способ прокладки» —
  текстовые; «Длина проводника», «Длина проводника в трубе», «Длина
  проводника в лотке» — числовые; «Имя нагрузки» — обычно нативный
  параметр Revit MEP.
- **Виды** (`OST_Views`): служебный текстовый параметр для манифеста
  структурной схемы (`manifest_param_name`) — привязать к категории
  «Виды», JSON туда пишет `BuildSkudSchematic`, вручную не редактировать.
  Аналог `layout_param_name` у СОТ.
- Не параметр, а соглашение: рабочий набор контроллеров и имя их типа
  должны содержать соответствующие ключевые слова; словарь «тип устройства
  → тип кабеля» и категории устройств для структурной схемы задаются
  ключевыми словами в окне настроек, не хранятся в репозитории; имя
  чертёжного вида схемы (`schematic_view_name`) — тоже настройка, не
  параметр модели.
