# Структурная схема СКУД: что подготовить и как это работает

Относится к кнопкам `SKUD.panel`: **Помещение точек прохода**
(`AssignSkudRooms`) и **Структурная схема** (`BuildSkudSchematic`). Общий
обзор панели — `docs/skud-panel.md`, справочник функций — `lib/README.md`.

---

## 1. Идея

Раньше `BuildSkudSchematic` раскладывал каждое устройство контроллера
отдельным схемным семейством по координатам категории. Теперь:

- один контроллер может обслуживать несколько **точек прохода**
  (дверей / турникетов);
- контроллер физически может стоять далеко от своих считывателей — на
  структурной схеме это неважно, схема топологическая;
- для каждой точки прохода есть **типовой узел** — заранее собранная
  Revit-**группа деталей** (считыватель + замок + кнопка выхода + геркон
  и т.п. + рамка);
- кнопка сравнивает **состав точки прохода** с составом каждой типовой
  группы, находит совпадающую, вставляет её на чертёжный вид,
  разгруппировывает и переносит адреса на схемные элементы;
- узел-контроллер вставляется один раз на контроллер и соединяется
  линией с каждой точкой прохода;
- состояние схемы (что где стоит, какой схемный элемент какому устройству
  соответствует) хранится в JSON **в служебном параметре чертёжного
  вида** (как раскладка СОТ/СПС), плюс каждый схемный элемент несёт
  `UniqueId` своего устройства в параметре;
- **повторный запуск той же кнопки — инкрементальная синхронизация:**
  неизменные точки прохода не трогаются (ручная раскладка сохраняется),
  изменившиеся перерисовываются, пропавшие удаляются, новые добавляются.
  Отдельной кнопки обновления нет.

«Состав» = мультимножество **категорий** устройств. Категория реального
устройства определяется **точным типом семейства** (не по ключевым
словам) — таблица «категория → реальные типы» задаётся в настройках.

## 2. Что подготовить (один раз на проект)

### 2.1. Параметры ФОП

Все — общие параметры проекта, вписываются в окно «Параметры СКУД» и
«Параметры помещений». Реальные имена — на усмотрение проекта.

| Параметр | Где | Тип | Обяз. | Зачем |
|---|---|---|---|---|
| «Адрес устройства» | экземпляр устройства и контроллера | текст | да | заполняется пайплайном СКУД; переносится на схему |
| «Марка устройства» | экземпляр устройства | текст | да | на схему пишется = адрес |
| «Номер точки прохода» | экземпляр устройства | текст/число | нет | делит устройства контроллера по точкам прохода; **пусто → одна точка прохода** |
| параметр адреса на схемном семействе | экземпляр Detail Component (схемные семейства) | текст | да | сюда кнопка пишет адрес/марку на схеме |
| `schematic_source_uid_param` | экземпляр Detail Component (схемные семейства) | текст | да | сюда кнопка пишет `UniqueId` исходного устройства — связь схема↔модель для инкрементальной синхронизации. Аналог `device_uid_param_name` у СОТ |
| служебный параметр манифеста | категория **«Виды»** (`OST_Views`) | текст | да | сюда `BuildSkudSchematic` пишет JSON всей схемы (состояние); вручную не трогать. Аналог `layout_param_name` у СОТ |
| имя помещения («Имя (Номер)») | экземпляр устройств и контроллеров | текст | да (для «Помещение точек прохода») | задаётся в «Параметры помещений» (`target_param_name`) |
| параметр номера помещения в связи | Room в файле-связи | текст | да (для «Помещение точек прохода») | «Параметры помещений» (`room_number_param_name`) |

### 2.2. Категории устройств схемы

В «Параметры СКУД» → поле **«Категории устройств схемы»** (по одной на
строку). Обязательно строка `контроллер`. Пример:

```
контроллер
считыватель
замок
кнопка выхода
геркон
доводчик
ИБП
```

### 2.3. Категория → реальные типы устройств (ключ идентичности)

В «Параметры СКУД» для каждой категории → **«Реальные типы устройств
этой категории (в модели)»** — мультивыбор из категорий Revit
`Охранная сигнализация` / `Электрооборудование`.

Именно по этой таблице кнопка понимает, что данный экземпляр в модели —
«считыватель». Если тип не отмечен ни в одной категории — устройство
попадёт в «без категории» и в сигнатуру не войдёт (об этом будет строка
в отчёте и в диагностике).

### 2.4. Категория → схемное семейство

В «Параметры СКУД» для каждой категории → **«Схемное семейство (для
вставки)»** — тип из категории `Элементы узлов` (Detail Items).

Нужно для двух вещей:
- **чтение состава типовых групп** — категория схемного элемента внутри
  группы определяется по его типу семейства;
- **резервная раскладка** (когда для точки прохода нет группы).

> Если типовые группы уже собраны из этих же схемных семейств —
> достаточно указать здесь тот же тип, что лежит в группе.

### 2.5. Типовые группы деталей

Собираются вручную в Revit **на чертёжном виде**:

**Узел-контроллер** (один):
1. вставить схемное семейство категории `контроллер`;
2. добавить рамку/подписи линиями детализации (по желанию — на расчёт
   не влияет);
3. выделить всё → **Create Group** (группа деталей);
4. оставить хотя бы один экземпляр группы в проекте.

**Узлы точек прохода** (по одному на каждый типовой состав):
1. для каждого устройства точки прохода вставить схемное семейство
   нужной категории (тип должен быть указан в п. 2.4). Для двусторонней
   двери — два семейства «считыватель», и т.д.;
2. рамка/подписи — по желанию;
3. **Create Group**;
4. оставить экземпляр в проекте (состав читается по **первому
   размещённому экземпляру**; если экземпляров нет — группа
   пропускается, в отчёте «не удалось прочитать состав групп»).

Имена групп — любые осмысленные (попадают в отчёт и в манифест).

Минимальный типовой набор:
- `СКУД_ТП_односторонняя` — считыватель + замок + кнопка выхода + геркон;
- `СКУД_ТП_двусторонняя` — считыватель ×2 + замок + геркон;
- дальше по мере надобности.

### 2.6. Выбор групп в настройках

«Параметры СКУД» → раздел **«Типовые группы структурной схемы»**:
- **Узел-контроллер** — выбрать одну группу деталей;
- **Узлы точек прохода** — мультивыбор всех типовых групп точек прохода.

Список показывает **только группы деталей** проекта.

### 2.7. Помещения

- Подгрузить связь(и) с размещёнными Room;
- «Параметры помещений» — заполнить `target_param_name` и
  `room_number_param_name`.

### 2.8. Чертёжный вид и служебные параметры

- В «Параметры СКУД» → `[Схема]` заполнить:
  - **«Имя чертёжного вида структурной схемы»** (`schematic_view_name`,
    по умолчанию `Структурная схема СКУД`);
  - **«Служебный параметр вида для хранения манифеста»**
    (`manifest_param_name`);
  - **«Служебный параметр схемного семейства для UniqueId исходного
    устройства»** (`schematic_source_uid_param`).
- Завести два общих параметра, оба **текстовые**:
  - `manifest_param_name` — привязан к категории **«Виды»** (в него
    кнопка пишет весь JSON состояния схемы);
  - `schematic_source_uid_param` — привязан к категориям **схемных
    Detail-семейств** (в него кнопка пишет `UniqueId` исходного
    устройства — по нему повторный запуск узнаёт «то же устройство»).
- Сам вид создавать не нужно — `BuildSkudSchematic` создаст Drafting View
  с этим именем при первом запуске и дальше будет его синхронизировать.
  Несколько схем параллельно — разные имена вида.

---

## 3. Что заполнять при моделировании

- **Адреса устройств** — как обычно, пайплайном СКУД
  (`AssignCircuitsAndCables` / `CalcSkudLengths`).
- **«Номер точки прохода»** — только там, где к одному контроллеру
  подключено **несколько** точек прохода: устройствам первой двери — `1`,
  второй — `2` и т.д. Где точка прохода одна — можно не заполнять.

---

## 4. Порядок запуска

1. Пайплайн СКУД до адресов устройств включительно.
2. **Помещение точек прохода** (`AssignSkudRooms`).
3. **Структурная схема** (`BuildSkudSchematic`) — вид создаётся/находится
   по имени сам, точку указывать не нужно.
4. При любых изменениях в модели — снова **Структурная схема**. Она сама
   находит изменения: неизменные точки прохода не трогает, изменившиеся
   перерисовывает. Отдельной кнопки обновления нет.

---

## 5. Как работает каждая кнопка

### 5.1. Помещение точек прохода (`AssignSkudRooms`)

1. Собирает контроллеры СКУД и их устройства (по цепям, как
   `AssignCircuitsAndCables`).
2. Делит устройства каждого контроллера по точкам прохода — по значению
   «Номер точки прохода» (пусто → точка прохода `1`).
3. Для каждого устройства ищет помещение в связях (та же механика, что
   «Помещение из связи»: точное попадание в Room, иначе ближайший контур
   в пределах допуска).
4. По точке прохода берёт **самое частое непустое** значение и пишет его
   **всем** устройствам точки прохода. При равенстве частот — первое по
   порядку (устройства отсортированы по адресу → результат стабилен).
5. Контроллеру помещение пишется индивидуально (без большинства).
6. Отчёт: сколько точек прохода обработано, сколько без помещения.

### 5.2. Структурная схема (`BuildSkudSchematic`) — инкрементальная синхронизация

Единый вход: и первая сборка, и обновление — это одна кнопка.

1. Находит чертёжный вид `schematic_view_name` (или создаёт новый Drafting
   View) и читает **состояние** из параметра вида `manifest_param_name`.
2. Читает сигнатуры типовых групп точек прохода: по первому размещённому
   экземпляру каждой группы → категории её схемных элементов →
   мультимножество `((категория, кол-во), …)`.
3. Строит **желаемое состояние** по модели: контроллеры с адресом → точки
   прохода (по «Номер точки прохода») → устройства (с `UniqueId`, адресом,
   категорией) → сигнатура → подобранная группа.
4. Синхронизирует с сохранённым состоянием (единица — **точка прохода**):
   - **узел-контроллер**: если его схемные элементы на месте — не трогает,
     только обновляет адрес; иначе ставит группу-контроллер заново,
     каждому элементу пишет `UniqueId` контроллера;
   - **точка прохода не изменилась** (тот же набор устройств по `UniqueId`
     и та же подобранная группа) → геометрию не трогает, обновляет только
     «Адрес устройства» / «Марка устройства» на схемных элементах;
   - **точка прохода изменилась** (набор устройств или группа) → удаляет
     её схемные элементы и рисует заново: `PlaceGroup` со смещением вниз
     от контроллера → разгруппировать → сопоставить схемные элементы
     устройствам по категории (в пределах категории — по адресу) → каждому
     записать `UniqueId` устройства, адрес, марку;
   - **точка прохода пропала** из модели → удаляет её элементы;
   - **новая точка прохода** → размещает;
   - **контроллер пропал** → удаляет его узел и все точки прохода.
5. **No-match** (для состава точки прохода нет группы) → резервная
   раскладка: схемные семейства по категориям столбиком вниз от точки
   прохода (шаг — `schematic_layout_step_mm`) + строка в отчёте с
   составом и просьбой собрать группу.
6. **Линии** контроллер→точка прохода пересоздаются каждый запуск; якорь —
   среднее положение фактических схемных элементов (следует за ручным
   перемещением).
7. Новое состояние пишется обратно в параметр вида. Если параметр не
   резолвится/только для чтения — предупреждение в окне вывода.
8. Отчёт: точек прохода не изменилось / перерисовано / добавлено / удалено;
   контроллеров добавлено / удалено; нерезолвившихся ссылок; no-match.

**На схеме групп не остаётся** — только детали и линии.

### 5.3. Диагностика (`InspectSchematicDevices`)

Выбрать контроллер → в окне вывода: все цепи, все элементы, дубли по
`ElementId`, **разбивка по точкам прохода с сигнатурой каждой** и
категорией каждого устройства. Отсюда видно, почему точка прохода не
подобрала группу (например, у устройства не назначена категория, или
состав отличается от всех типовых групп).

## 6. Ограничения и заметки

- **Манифест хранится в параметре чертёжного вида** и привязан к
  `ElementId` конкретного файла. «Сохранить как» в новый файл — манифест
  переедет вместе с видом, но `ElementId` устройств станут другими:
  запустить «Структурную схему» заново (она перерисует по свежим id).
- **Дублировать вид** структурной схемы нельзя — копия унесёт тот же
  манифест, и два вида будут спорить за один набор id. Для второй схемы
  задавайте другое имя вида в настройках.
- Параметр `manifest_param_name` должен быть **записываемым на виде**
  (не залочен шаблоном вида, тип — «Строка»). Если запись не удалась —
  строка в окне вывода; следующий запуск не увидит прошлого состояния и
  соберёт всё заново.
- **Совпадение сигнатур точное.** Лишний доводчик или недостающая кнопка
  выхода → точка прохода уйдёт в резерв. Это же помогает ловить ошибки
  модели: в отчёте будет назван фактический состав.
- **Ручную раскладку** можно и нужно править: неизменные точки прохода
  повторный запуск не двигает. Но если поменять состав точки прохода или
  тип подобранной группы — эта точка прохода будет перерисована с нуля в
  расчётной позиции (остальные не тронуты).
- **Новая точка прохода** ставится в расчётной позиции (вертикально под
  контроллером, шаг 1/3 от «шага между контроллерами») — может наложиться
  на вручную передвинутую соседнюю; растащить руками.
- Если `schematic_source_uid_param` не заполнен у элементов (не завели
  параметр) — при повторном запуске часть связей теряется, точки прохода
  чаще перерисовываются целиком. Параметр обязателен.
- **Резервная раскладка** ставит устройства простым столбиком (шаг —
  `schematic_layout_step_mm`), работает только если для категорий заполнено
  «Схемное семейство» (п. 2.4); для категорий без схемного семейства по
  этой точке прохода будет только строка в отчёте. Per-category координаты
  и превью раскладки из настроек убраны — основной путь через группы.
- Каждая типовая группа должна иметь **хотя бы один размещённый
  экземпляр** — иначе её состав не прочитать.
